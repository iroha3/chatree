## D-001 多个根 / 多个系统提示词节点同屏

- **状态**：⏸ 押后
- **背景**：用户提「新的 system prompt 节点，这样相关的主题都能在画布上聊」。
- **选项**：A. 一个会话多个根；B. 保持「一会话一根」，另做「会话并排」→ 见 D-002。
- **结论**：**暂时都不做。** 两个原因：
  1. **数据结构其实不用改。** `Session.nodes: ChatNode[]` + `parentId` 本来就是一片**森林**，
     `parentId: null` 的节点天然可以有 N 个。真正把它当成「单树」的只有下面 4 处代码 +
     1 个入口（**都不是 schema**）：
     - `runNodeGeneration` 用 `find(n => n.type === 'system')` 取提示词 —— 应改成
       **沿父链向上找最近的 system 祖先**（这本来也是隐患：有第二个根时会拿错）；
     - `calculateNodeLayout` 只从第一个 system 节点布局，其它根在强制重排时会落到 `{0,0}`
       叠在一起 —— 应改成**遍历所有根**，根与根之间留横向间距；
     - 「`systemNodes.length > 1` 就删」的去重 effect 必须改 —— 否则第二个 system 节点会被
       立刻删掉。应只保留**窄口径**清理（无子节点、内容为空/与首个相同、`systemPromptTouched
       !== true` 的 StrictMode 残留）；
     - 没有「新建主题（新根）」的入口。
     - 已经天然支持的：`buildFlowEdges`（按 `parentId`）、`homeViewport`（量包围盒）、
       `buildMindMapTree`（按「无父或父失踪者为根」遍历）、删除（按子树）。
  2. **成本在认知，不在代码。** 多根会把「一个会话 = 一个主题」变成「一个会话 = 一个工作区」：
     导航（我在哪个根里？）、标题、统计都会变浑。这个负担**所有用户一起付**，而真正用到的
     可能很少。
- **触发条件**（满足任一条再回来看）：
  1. 自己连续三次真实地冒出「这两个要是在一张画布上就好了」；
  2. 有用户明确提这个需求；
  3. 出现「反复对比不同 persona / 系统提示词」的高频工作流（比如酒馆那一类）。
- **相关代码**：`ChatFlow.tsx`（`runNodeGeneration`、`calculateNodeLayout`、去重 effect、
  根节点 seed）。

## D-002 会话并排 / 分屏

- **状态**：⏸ 押后（**很可能是错的，别急**）
- **背景**：D-001 的替代方向 —— 保留「一个会话一个根」，把两个会话并排看。
- **选项**：A. 分屏（两个独立 `<ChatFlow>`）；B. 只做「快速切换」（不并排）。
- **结论**：**暂不做。**
  - **物理上放不下。** 卡片宽 **516px**，带两个兄弟分支的树宽 ≈ `516×2 + H_GAP 220` =
    **1252px**。1440px 笔记本减侧栏 ~260 后两等分 = 每格 **590px**；要塞下 1252px 得缩到
    **zoom ≈ 0.4**，19px 正文变 ~8px，读不了 —— 两边都看不清，最后还是得放大/拖动。
  - **连极客都不喜欢分屏。** 用户原话：「我想到 tmux，我还是不太喜欢 tmux 的分屏」。
    tmux 里真正被爱的是 `Ctrl-b n/p` 秒切，不是 `%` 分屏。**该抄的是切换，不是分屏。**
  - 真正的需求大概率只是「快速在两个会话之间来回看」——那是**切换**能解决的，
    而侧栏已经有点击 / 全文搜索 / 按最近排序 / 文件夹。
  - 若将来真做，MVP 是：副窗格**只读**（可缩放/平移/双击阅读）+「提升为主窗格」+ 关闭；
    副会话 id / 联动 / 分隔位置都是 App 级 UI state，**不落库**（数据契约见 `DEV.md` §1）。
  - ⚠️ **不要用「开两个浏览器标签 / 桌面版多窗口」代替**：两个标签的 zustand store 不共享，
    IndexedDB 是同一个但内存态是旧的，会各写各的、互相覆盖。要做必须在同一 App 实例内。
- **触发条件**：同 D-001（连续多次真的想并排、有人提、或对比工作流变高频）。
- **相关代码**：`App.tsx`（`main` 里渲染 `<ChatFlow>`）、`ChatFlow.tsx`（`ReactFlowProvider`）。

## D-003 导出其它格式（PDF / DOCX / 独立 HTML / Markdown）

- **状态**：⏸ 押后
- **背景**：想要「一个导出按钮，能出 PDF / MD / DOCX / JSON / 导图」。
- **已完成的第一步**：画布右上角原来平级的「导出 JSON」+「思维导图」两个图标，已合成一个
  **分享按钮（`Share2`）→ 下拉菜单**（备份 JSON / 思维导图 .mm），位置见 `ChatFlow.tsx` 的
  `showExportMenu`；以后加格式就往这个菜单里塞。**后面的格式本身押后。**
- **调研（2026-09）**：豆包 / ChatGPT / 千问这类头部 C 端都**不给用户级导出**；它们做的是
  「转为文档编辑」（Canvas / 文档模式）。ChatGPT 的对话导出藏得很深（设置 → 数据控制，
  给 GDPR 用的），不是产品功能。
  - 读法：**不导出是它们的商业模式（锁定），不是需求不存在** —— 本地优先工具恰恰相反，
    数据本来就是用户的。但「转为文档编辑」这个信号是真的：用户想把对话**拿出去继续改**，
    而不是归档成 PDF。
- **判据**：自己的数据用 JSON 就够了（已解决）。剩下所有格式只服务两种人：**没有 Chatree 的
  收件人**、**要粘进 Word / 别的工具继续改的自己**。没有这两个场景就不做。
- **HTML ≠ JSON**：JSON 是「原件」（给 Chatree、可再导入、与 schema 绑定）；HTML 是「快照」
  （给任何有浏览器的人、不依赖 Chatree 存活、手机上能看）。但对「文件只在未来的我手里、而
  那时的我还在用 Chatree」而言，两者确实没区别 —— 这就是导出整体可以先押后的原因。
- **别用「格式」跟用户说话，要用「拿来干嘛」**（用户提醒：别犯知识的诅咒 —— 学生 / 同人文 /
  酒馆玩家这类非技术用户也会玩分支，不能默认他们会渲染 Markdown）：
  - 存档 / 以后接着用 → JSON 备份（已有）
  - 给别人看 / 打印 / 交作业 → PDF、**独立 HTML**
  - 要接着改 / 二次创作 → DOCX、Markdown
  - Markdown 从「门面」降级成「高级格式」：它是内部的中间产物（MD → HTML/PDF/DOCX），
    非技术用户不需要认识它。
- **独立 HTML**（重点候选）：单文件 `.html`，双击就能看、离线、手机上也能开、不用装东西；
  可保留分支（可折叠 / 沿路径切换）。零依赖。能同时回答「保留非线性」和「非技术用户友好」。
- **非线性对话 → 线性文档**（核心难题，树有分叉、文档是线性的）：
  - A. 只导「当前选中路径」（根 → 某节点）—— 和「连续阅读」「复制路径为 Markdown」共用路径提取；
  - B. 导整棵树：主干 DFS，分支作缩进小节/附录，标「分支自节点 X」；
  - C. 导前在画布上框选节点。
  - 倾向 A 作默认 + B 作「整棵树」选项，但都得先有路径提取那个纯函数。
- **PDF 技术选型**：
  - 路线 1：`window.print()` + 打印样式。零依赖，中文用系统字体（不糊、不下载），用户自己
    「另存为 PDF」。代价：页眉页脚/页码/分页控制弱。**推荐先走这条。**
  - 路线 2：**pdfmake**。参考 `tmp/tmp.js`（OmniChat Exporter 油猴脚本）：`pdfmake@0.2.9` +
    `vfs_fonts.js`（cdnjs），把 HTML 转成 pdfmake 的 docDefinition，输出**矢量文字、可选中**，
    不是截图；中文靠**按需下载 Noto 字体**（`NotoSansCJKsc-Regular.otf`，`GM_xmlhttpRequest`
    从 GitHub 拉，注入 `pdfMake.vfs`），`franc-min` 做语言检测决定下哪些字体。
    ⚠️ 违反「零 CDN / 离线优先」：要么子集化 CJK 字体打进 `public/`（体积大），要么联网下载
    （离线不可用）。所以排在 print 之后。
  - 路线 3：html2canvas + jsPDF：截图式，中文没问题但**不可搜索、体积大**，不推荐。
- **DOCX**：至少一个生成库（`docx` 等，动态 import）。也可退而求其次生成「HTML 存成 .doc」
  （Word 能开、样式差）。
- **落地顺序建议**：Markdown → PDF(print) → DOCX，先看 PDF 顺不顺。
- **触发条件**：真出现「要把对话发给一个没有 Chatree 的人」或「要粘进 Word 继续改」的场景。
- **相关代码**：`utils/sessionTransfer.ts`（JSON）、`utils/exportUtils.ts`（导图）、
  `ChatFlow.tsx` 的 `showExportMenu`。

## D-004 键盘快捷键的边界

- **状态**：✅ 已定（已写进 `DEV.md` §3.13）
- **结论**：**只在「局部语义明确」的地方用键，不做全局画布快捷键。** 现有的键全是上下文型的：
  输入框 `Esc`/`Ctrl+Enter`、弹窗 `Esc`/`Enter`、阅读浮层 `Esc`、`Ctrl+滚轮` 缩放。唯一的
  画布级快捷键（Backspace/Delete 删节点）是**刻意关掉**的（`deleteKeyCode={null}`，见 `DEV.md` §3.1）。
- **理由**：① 画布上到处是 textarea，全局键要不停判断「用户是不是在打字」；② 破坏性全局键会
  绕过确认/撤销；③ 本应用是**可见按钮 + 鼠标优先**的，快捷键是第二套隐形界面且不可发现。
- **推论**：「快速切换会话」**不建议加全局快捷键** —— 侧栏已经够快；真要加键，并进
  `ROADMAP` 的「⏸ 快捷键补齐」一起评估，不单独做。
- **相关代码**：`ChatNode.tsx` / `SystemNode.tsx` / `ConfirmDialog.tsx` / `NodeReadOverlay.tsx`。

## D-005 长内容的折叠边界

- **状态**：📋 偏 TODO（方向大致定了，只差动手）
- **背景**：目前只有「思考链」可折叠，其余部位是否引入折叠还没拍。
- **已经想清的**：
  - **思考链**：已是最优形态（思考中自动展开 → 结束安静折叠 → 用户手动干预后不再自动），不动。
  - **系统提示词**：倾向折叠成 2 行预览 —— 它是同一批兄弟节点**共享的样板**，每张卡都铺一遍
    纯占地方，而且通常写完就不动。待定：默认折，还是只把高度压小。
  - **用户提问**：倾向**不给**折叠。只读态已有 `max-h-[200px]` + 滚动，够用；给用户自己写的
    东西加折叠，反而让人怀疑「我是不是漏看了」。
  - **LLM 回答**：倾向**不给手动折叠开关**，改成「**太长才自动收**」：短回答不动；超过阈值
    （约 800 字 / 20 行）收成前 8 行 + 底部渐隐 + 「展开全文 · 共 N 字」，全文仍可一键展开。
    - 为什么需要上限：卡片宽固定 **516px**、`V_GAP` 只有 **48**。一条 3000 字的回答会变成
      5000px 高的卡，纵向节奏崩、兄弟分支没法并排比较 —— 而并排比较正是这个应用存在的理由。
    - 为什么**反对默认折叠**：回答是这张卡的全部意义，默认藏 = 每张卡都要点一下；
      而「一眼扫完几条兄弟分支的差异」是树状视图的核心用途。
  - ❌ 折叠状态**不落库**（纯 UI `useState`）：写进 node 会污染导出格式（见 `DEV.md` §1）。
- **触发条件**：真有长回复把画布搞乱时再回来定阈值和形态。
- **待定**：① 系统提示词默认折还是只压高度；② 回答阈值定多少（或先不做）；③ 就地展开 vs
  直接开阅读浮层（倾向**就地展开** —— 浮层会盖住整棵树，对比的上下文没了）。

## D-011 Windows ARM64 包

- **状态**：⏸ 押后
- **结论**：`windows-11-arm` 现在**不能出**。Pake 3.17.1 的文件名 bug：Tauri 产出
  `Chatree_0.1.0_arm64_en-US.msi`，而 Pake 去找 `Chatree_0.1.0_aarch64_en-US.msi`
  （`ARCH_DISPLAY_NAMES.arm64 = 'aarch64'`），于是 ENOENT → `BUILD_FAILED`；而且报错发生在
  `copyRawBinary` 之前，**连原始 exe 都不会被拷出来**。
- **可选项**：① 等上游修（升 Pake 版本后重试）；② 在 `scripts/pake.mjs` 加一层兜底：从报错
  路径反推出 target 目录，直接扫 `bundle/**` 里真正的产物。
- **现状**：**Windows on ARM 直接跑我们的 x64 包**（系统自带 x64 模拟）就够用。

## D-012 单链长对话「走不动」：滚轮改成平移（而不是改布局）

- **状态**：✅ 已定（已实现）
- **背景**：用户「聊 20 轮变成一长串根本没法看」，当成「纯单链布局优化」提的。
- **选项**：
  - A. 改布局：缩 `V_GAP` / 折成蛇形 / 另做阅读视图；
  - B. 改交互：滚轮 = 平移画布，`Ctrl`/`⌘` + 滚轮 = 缩放，并按滚动链让内层先滚。
- **结论**：先做 B。
  - 聊天记录本来就是「**滚着读**」的，正常滚一下就行；而这里 React Flow 默认
    **滚轮 = 缩放**（`zoomOnScroll` 默认开、`panOnScroll` 默认关），想往下走只能**拖**。
    所以「没法看」是**移动问题，不是长度问题** —— 20 屏在聊天软件里很正常。
  - 叠上第二个坑：卡片在非 Ctrl 滚轮时 `stopPropagation`，而卡片宽 516px、占了画布大部分
    面积，鼠标停在卡片上就什么也动不了，体感就是「卡死」。
  - A 先不动：单链在画布上就是一条竖线，这本身不算错，没必要为它改树形布局的常量。
- **触发条件**（什么情况才回头做 A）：B 上线、真的用过一阵后，仍然觉得「笔直一串」难看。
- **相关代码**：`ChatFlow.tsx` 的 `panOnScroll`、`src/utils/wheelChain.ts`；约定见 `DEV.md` §3.14。
- **结案**：阅读视图（D-013）上线后用户直接拍板「**不用了，我们更优雅地解决了**」——
  布局常量（`V_GAP` / 蛇形折叠）**不再调**。竖向一条长链本身没问题，问题一直是「走不动」。

## D-013 连续阅读：切换兄弟分支的语义

- **状态**：✅ 已定（已实现）
- **背景**：双击节点从「读一个节点」升级成「读整条路径」（见 `DEV.md` §3.15）。路径经过分叉
  时，右侧要能列出兄弟分支并切过去 —— 但「切过去」到底切到哪里？
- **选项**：
  - A. 把阅读终点改成被点的那个节点 —— 路径停在它自己；
  - B. 自动沿它「最新创建的那个孩子」一路走到最深 —— 一次点到位；
  - C. 弹出整棵子树让你选。
- **结论**：**A**。B 看着聪明，但它在替用户猜「你想读哪一条」；而分叉本身还可以再分叉，
  猜错了反而更迷惑（也是「为想象中的用户做聪明事」）。C 太重。
  A 可预测性最好：点谁就是读谁；想继续往下读，终点卡片后面有「从这条继续」（列出直接
  子节点），一步一层，永远不猜。
- **补充（手感要和点击一致）**：滚轮翻页必须用和点分支**同一种平滑滚动**，不能图省事用
  `behavior: 'auto'` 瞬间到位 —— 瞬间跳会让读者丢掉空间感（不知道内容去哪了）。另外翻到的
  卡片要有**落点高亮**，明确回答「我现在读到哪了」。「避免和平滑滚动打架」的正确做法是给
  起步阶段加个短锁（`advanceLockRef`），不是牺牲动画。
- **补充（自动翻页）**：「读到底继续滚 → 下一轮」只在**恰好一个后续**时生效。有分叉时
  自动翻就必须替用户选一条 —— 又回到「猜」的毛病上，所以有分叉只给按钮。另外要**多滑一截**
  才翻（阈值，见 `DEV.md` §3.15），避免「最后一行还没读完就被顶走」。
- **触发条件**：实际用下来觉得「一层一层点」太烦，再考虑 B。
- **相关代码**：`components/nodes/PathReaderOverlay.tsx`、`utils/tree.ts`。

## D-014 跨会话 token / 花费累计

- **状态**：🚫 不做
- **背景**：想在侧栏 / 统计里看「一共花了多少 token / 多少钱」。
- **结论**：**不做。**
  1. 我们的用量数字是**服务商返回的**，不是本地估算的（`src/utils/usage.ts`），只在请求回来时
     才知道。要累计就得长期维护一份「历史总数」，还要处理导入 / 删除 / 改模型带来的对账问题。
  2. 真实花费由服务商后台说了算（充值、赠送、缓存价、阶梯价），我们算出来的数字**一定和账单
     对不上** —— 对不上的数字比没有数字更糟。
  3. 这不是这个应用存在的理由（树状分支对比）。
- **触发条件**：出现「按会话 / 按天看用量」的真实高频需求，且能接受它是**估算**。
- **相关代码**：`src/utils/usage.ts`、`src/components/SessionStats.tsx`。

## D-018 桌面整卡拖拽 vs 触屏滚内容

- **状态**：✅ 已定（已实现）
- **背景**：卡片正文区一度被钉上 `nodrag` 来保住触屏滚动，代价是 PC 鼠标在正文空白处
  也拖不动卡片；反过来，为了桌面手感放开 `nodrag`，触屏上手指一滑又把卡片拖走。
- **选项**：
  - A. 按主指针类型分流：鼠标 = 整卡可拖（正文不写 `nodrag`），触屏 = 只认标题栏把手
    （React Flow `dragHandle`），正文留给原生滚动；
  - B. 正文永远 `nodrag`，谁也别想从正文拖卡片；
  - C. 两个都要：正文既能选文字又能拖卡片（靠长按 / 阈值区分）。
- **结论**：**A**。两种设备的直觉本来就不一样 —— 鼠标不会「按住上下搓来滚页面」，所以
  按住就是拖；手指滑动必须留给滚动。C 需要劫持手势阈值，误判一次就是「我明明想选字
  结果卡片飞了」，不值得。B 则直接牺牲桌面手感。
- **已知代价**：桌面端在正文区**按住拖动选择文字**会让位给拖卡片（d3-drag 会 `user-select: none`）。
  想选字用双击 / 三击或键盘；这个取舍接受。
- **触发条件**：真有人抱怨「不能拖选正文」且高频到碍事，再考虑 C（长按拖选）。
- **相关代码**：`ChatFlow.tsx` 的 `isCoarsePointer` / `buildFlowNode`、`index.css` 的
  `.node-drag-handle` 与 `touch-action` 覆盖；契约与坑见 `DEV.md` §3.16 / §4.6-4.7。
